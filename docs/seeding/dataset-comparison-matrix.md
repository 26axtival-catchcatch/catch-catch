# 데이터셋 확장 비교 매트릭스

> 목적: 같은 질문과 같은 기간으로 분석 범위만 넓혔을 때, **데이터가 많아져서 그럴듯한 답이 나온다**가 아니라, 앞선 두 데이터셋으로는 관측할 수 없던 고객 행동과 업무 상태가 확인되어 더 실행 가능한 인사이트가 나온다는 것을 보여준다.

## 1. 비교 규칙

- 기준 기간: `2026-09-04 ~ 2026-09-10` (개선안 적용 전 7일)
- 고정 조건: 질문, 기간, 고객 연결키는 바꾸지 않는다.
- 변경 조건: 사용할 Source만 `A+B`에서 `A+B+C+D`로 확장한다.
- 해석 원칙: `A+B`에서 고객이 안 보인다는 결과는 **문제가 없음/0명**이 아니라 **현재 Source로 판단 불가**다.

| 기호 | 공통 역할 | 실제 Source | 연결키 | 이 데이터로 답하는 질문 |
| --- | --- | --- | --- | --- |
| A | 고객이 무엇을 찾았는가 | `hackathon_search_history` (AI 검색 이력) | `CZ_LNK_KEY` | 검색어, 반복 검색, 검색 결과 |
| B | 고객이 언제 사람에게 도움을 청했는가 | `hackathon_voc` (상담 이력) | `CZ_LNK_KEY` | 문의 내용, 상담 전환, 상담 처리 |
| C | 고객이 앱 안에서 실제로 어디를 거쳤는가 | `hackathon_app_behavior` (앱 행동) | `CUST_NO` | 세션, 화면·메뉴 이동, 이탈 단계, 재시도 |
| D | 고객의 업무 상태가 실제로 무엇이었는가 | 도메인별 업무 Source | `CUST_NO` 또는 `CZ_LNK_KEY` | 가입·이용·완료 상태, 상품 또는 금액 |
| E | 어떤 고객 커뮤니케이션이 선행했는가 | `hackathon_crm_campaign` (CRM 발송 이력) | `CZ_LNK_KEY` | 캠페인 대상, 발송 시점·결과, 안내 상품과 기능 |

`A+B`는 고객이 **표현한 신호**를, `C+D`는 고객이 앱 안에서 **보인 행동과 실제 상태**를 보강한다.

| 도메인 | 고정 질문 | A+B: 확인 가능한 사실 | A+B만으로 말할 수 없는 것 | C+D 추가 Source | A+B+C+D: 새로 검증되는 인사이트 | 시딩 기준 검증값 |
| --- | --- | --- | --- | --- | --- | --- |
| 부가서비스 | `부가서비스 메뉴를 찾느라 반복 탐색한 고객 중 검색이나 상담에 나타나지 않은 고객도 찾아줘.` | 반복 검색과 메뉴 위치 문의, 상담 전환 | 검색·상담에 없는 고객의 규모, 실제 메뉴 미도달 여부, 가입 서비스 맥락 | C: `hackathon_app_behavior`<br>D: `hackathon_vas_subscription` | **조용한 탐색 고객 160명**을 새로 포착하고, 그중 **메뉴 미도달 이탈 16명**을 구분한다. 오답 메뉴 이동·상위 메뉴 복귀와 고객별 가입 서비스 3개를 함께 확인해, 조회/해지 진입 경로 개선의 근거를 만든다. | 메뉴 탐색 340명 · 즐겨찾기 84명 · 전체 미도달 97명 · 상담 전환 61명 |
| 소액결제 | `소액결제 한도 변경이 끝나지 않은 고객의 반복 시도 단계와 이용 특성을 분석해줘.` | 한도 변경 실패 문의와 상담 내용 | 미완료 전체 규모, 고객별 재시도 횟수, 동의/인증 중 어느 단계에서 멈췄는지, 정상 완료 고객과의 차이 | C: `hackathon_app_behavior`<br>D: `hackathon_billing_profile` | **미완료 210명, 567회 시도**를 확인하고 동의 바텀시트 이탈과 인증 실패를 구분한다. **완료 대조군 90명** 및 소액결제 이용금액 차이를 연결해 사전 안내·선택값 보존 실험의 대상을 특정한다. | 미완료 평균 2.7회 재시도 · 동의 단계 이탈 465회(약 82%) · 상담 전환 74명 |
| 로밍 | `로밍 요금제를 알아본 고객의 가입 여정과 개선 기회를 찾아줘.` | 로밍 관련 검색과 상담사의 요금제 가입 처리 | 상담 가입 고객이 앱에서 상품을 비교한 뒤 이탈했는지, 처음부터 상담을 선호했는지, 실제 상품이 활성 가입됐는지 | C: `hackathon_app_behavior`<br>D: `hackathon_roaming_usage` | 상담 가입 70명 중 **앱에서 요금제 3개를 비교한 뒤 이탈한 56명**과 **바로 상담을 요청한 14명**을 분리한다. 이탈 후 상담 가입과 실제 로밍 상품 등록을 연결해 비교 안내·가입 CTA 개선 기회를 검증한다. | 기준 구간 전체 140명 · 앱 탐색 후 이탈/상담 가입 56명(40%) · 바로 상담 14명 |

## 3. 발표용 핵심 비교: 부가서비스

### Run 1 — 제한 탐색: A+B

| 분석 입력 | 결과 표현 | 신뢰 가능한 결론 |
| --- | --- | --- |
| A `AI 검색 이력` + B `상담 이력` | 반복 검색과 “부가서비스 조회/해지 메뉴 위치” 문의가 보인다. | 고객이 메뉴 위치를 어려워하고 상담으로 이어지는 **표현된 문제**는 보인다. 다만 검색·상담에 나타나지 않은 고객이나 앱 내 이탈 경로는 알 수 없다. |

**결과 화면에서 반드시 보여줄 제한 문구**

> 검색 또는 상담으로 나타난 고객만 관측됩니다. 검색·상담에 나타나지 않은 고객의 규모와 메뉴 미도달 여부는 현재 데이터로 판단할 수 없습니다.

### Run 2 — 확장 탐색: A+B+C+D

| 추가 입력 | 새로 연결되는 사실 | 인사이트의 변화 |
| --- | --- | --- |
| C `앱 행동` | 앱에서 조회/해지 메뉴를 찾으려 한 고객 340명, 검색·상담 모두에 없는 조용한 탐색 고객 160명, 그중 메뉴 미도달 이탈 16명 | “상담 문의가 있다”에서 **지원 채널에도 잡히지 않는 탐색 실패 고객군이 있다**로 확장된다. |
| D `부가서비스 가입` | 조용한 탐색 고객의 가입 서비스 맥락(각 3개 상품) | 단순한 메뉴 방문 분석이 아니라, **관리할 서비스가 있는 고객이 조회/해지 메뉴에 도달하지 못하는 문제**로 행동의 맥락을 확인한다. |

**확장 Run의 검증 가능한 결론**

> 검색과 상담 데이터만으로는 보이지 않던 조용한 탐색 고객 160명이 앱 행동에서 확인됩니다. 이 중 16명은 부가서비스 조회/해지 메뉴에 도달하지 못했습니다. 가입 서비스 정보를 함께 연결하면, 관리 대상 서비스가 있는 고객에게 메뉴 진입 경로를 먼저 안내할 개선 기회를 검증할 수 있습니다.

### Run 3 — 원인 맥락 확장: A+B+C+D+E

같은 질문 `부가서비스 관련 검색이 증가한 배경과 고객의 실제 의도를 찾아, 추적할 시그널을 제안해줘.`를
유지하고 CRM 발송 이력만 추가하면 다음 연결이 생깁니다.

| 추가 입력 | 새로 연결되는 사실 | 인사이트의 변화 |
| --- | --- | --- |
| E `CRM 발송 이력` | 9월 7일 구글 원 옵션 변경 SMS 수신 240명 중 160명(66.7%)이 발송 이후 변경 의도 검색. 비수신 100명 중 검색은 20명(20.0%) | “해지/메뉴 문제로 검색이 늘었다”에서 **안내 캠페인이 기존 가입자의 옵션 변경 수요를 촉발했다**로 우선 해석이 바뀐다. 수신군 변경 검색률을 상·하단 밴드로 추적하고, 반복 검색 실패율은 해결 품질의 보조 지표로 둔다. |

## 4. 결과를 ‘더 좋은 인사이트’로 보이게 하는 화면 구성

같은 질문의 결과 카드 두 장을 나란히 둔다. 왼쪽은 실패가 아니라 **관측 한계**, 오른쪽은 **새로 검증된 행동·상태**를 강조한다.

| 화면 요소 | A+B 제한 Run | A+B+C+D 확장 Run |
| --- | --- | --- |
| 데이터 칩 | `A 검색` `B 상담` | `A 검색` `B 상담` `C 앱 행동` `D 부가서비스 가입` |
| 헤드라인 | “반복 검색·상담 문의는 보이지만 전체 규모는 판단 불가” | “지원 채널에 나타나지 않은 조용한 탐색 고객 160명 발견” |
| 대표 수치 | 검색·상담에 나타난 고객만 관측 | 조용한 탐색 160명 / 그중 메뉴 미도달 16명 |
| 근거 체인 | 검색어 → 상담 문의 | 검색어 → 앱 메뉴 이동/미도달 → 가입 서비스 상태 → 상담 |
| 액션 | 추가 데이터 연결 필요 | 조회/해지 메뉴 진입 CTA·추천 질문을 우선 실험 |

## 5. 발표 멘트

“처음에는 검색과 상담, 두 데이터만으로 분석했습니다. 반복 검색과 메뉴 위치 문의는 확인됐지만, 이 결과만으로는 ‘문제가 있는 고객이 몇 명인지’도 ‘앱에서 어디서 막혔는지’도 말할 수 없었습니다. 그래서 같은 질문과 기간을 유지한 채 앱 행동과 부가서비스 가입 데이터를 추가했습니다. 그 결과 검색이나 상담에 전혀 나타나지 않던 조용한 탐색 고객 160명과, 그중 메뉴에 도달하지 못한 16명을 확인했습니다. 데이터셋이 늘어서 답변이 길어진 것이 아니라, 이전에는 보이지 않던 고객 행동과 실제 가입 맥락이 연결돼 바로 실험할 수 있는 인사이트가 된 것입니다.”

## 6. 해석 경계

- 이 데이터는 메뉴 구조가 이탈의 **원인**임을 증명하지 않는다. 앱 로그는 탐색·미도달 패턴을, 가입 정보는 고객 맥락을 보여준다.
- 발표에서는 “메뉴 구조가 문제다”보다 “조회/해지 메뉴 진입 경로를 개선할 **기회가 확인됐다**”라고 표현한다.
- 확장 Run도 모든 Source를 무작정 넣는 방식이 아니다. 질문에 필요한 `C`와 도메인별 `D`만 추가해, 무엇이 인사이트를 가능하게 했는지 명확히 보인다.
