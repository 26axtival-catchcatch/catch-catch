# 해커톤 2주 합성 데이터 실행 안내

## 1. 데이터 생성

저장소 루트에서 다음 명령을 실행합니다.

```bash
make seed-hackathon
```

명령은 `data/seeding/hackathon-2week/`에 8개 원시 CSV, `daily_kpis.csv`,
`manifest.json`, 시스템 등록용 `onboarded-sources/`를 생성합니다. 같은 seed를 사용하면
CSV 체크섬이 동일합니다. Make 명령은 의도적으로 `--force`를 사용해 기존 생성물을
검증된 새 결과로 교체합니다.

기존 `exploration-evaluation-rubric.json`은 보존합니다. 이 파일은 기존 두 사례의 평가용이며
에이전트 Source로 등록하지 않습니다. 로밍 사례는 시딩 테스트와 `manifest.json`의
`exploration_cases` 검증 대상으로 추가합니다. seed `20260831`은 재현성 식별자이며
데이터의 관측 날짜를 뜻하지 않습니다.

직접 CLI를 실행할 때는 출력 경로를 명시해야 합니다.

```bash
uv run --project backend python -m customer_signal.seeding.cli \
  --output data/seeding/hackathon-2week \
  --seed 20260831 \
  --force
```

해지 수요가 아니라 안내 직후 발생한 옵션 변경 수요였다는 업무 맥락을 확인할 수 있습니다.
소액결제 시나리오는 한도 변경의 동의 단계 이탈, 재시도, 검색, 상담 이동을 보여줍니다.
로밍 시나리오는 요금제를 알아보다 앱에서 나간 뒤 상담사를 통해 가입한 고객을
보여줍니다. 앱의 요금제 비교와 이탈, 상담 처리, 실제 로밍 상품 가입 기록을 연결해
이 여정을 확인합니다. 상품은 모두 출국 당일 시작합니다. 세 사례의 조건과 대조군은 [시나리오 명세](./scenario-catalog.md)에
정리했습니다.

## 4. 시스템 실행

해커톤 데모는 Gemini 실모드를 기준으로 실행합니다. 환경 파일을 shell에서 `source`하지
않고 Backend 실행 명령에만 전달합니다.

```bash
ENV_FILE=.env \
ONBOARDED_SOURCES_DIR=data/seeding/hackathon-2week/onboarded-sources \
  bash scripts/dev.sh gemini
```

- Backend: `http://127.0.0.1:8000`
- Frontend: `http://127.0.0.1:3000`
- Swagger: `http://127.0.0.1:8000/docs`

`GET /api/sources`에는 다음 8개 Source가 추가로 표시되어야 합니다.

- `hackathon_app_behavior`
- `hackathon_search_history`
- `hackathon_search_feedback`
- `hackathon_crm_campaign`
- `hackathon_voc`
- `hackathon_vas_subscription`
- `hackathon_billing_profile`
- `hackathon_roaming_usage`

`scripts/dev.sh`는 선택한 환경 파일을 Python import 전에 `uv run --env-file`로 전달하고,
Frontend 프로세스에서 Gemini와 관측성 환경변수를 제거합니다.

Fixture는 외부 호출 없이 Source 등록과 화면 배선만 점검할 때 선택적으로 사용합니다.
해커톤 발표 결과 검증에는 사용하지 않습니다.

기존 Backend가 실행 중이면 재시딩 후 다시 시작해야 합니다. Source 목록과 데이터 범위는
프로세스 시작 시 로드됩니다.

## 5. 데모 조회 순서

1. 시작일 `2026-09-04`, 종료일 `2026-09-11`로 기준 구간 분석
2. `hackathon_search_history`, `hackathon_voc` Source 선택
3. `반복 행동 뒤 상담으로 전환되는 Journey를 보여줘.` 질문 실행
4. 리포트의 반복 검색, 상담 전환 근거와 권장 액션 확인
5. 시작일 `2026-09-11`, 종료일 `2026-09-18`로 같은 질문 재실행
6. 매칭 고객과 `daily_kpis.csv`의 2026-09-11 이후 개선 곡선 비교

종료일은 미포함입니다. 전체 14일 조회는 시작일 `2026-09-04`, 종료일 `2026-09-18`입니다.

Frontend에서는 필수 기본 `search_history` Source가 함께 선택됩니다. 이 Source는 해커톤
분석 기간 밖의 데이터만 가지므로 위 기간의 매칭 수에는 영향을 주지 않습니다.

추천 질문은 다음과 같습니다.

- `부가서비스 조회/해지 메뉴를 찾기 전 반복 탐색과 상담 전환 패턴을 분석해줘.`
- `소액결제 한도 변경 중 이탈 단계와 반복 시도 고객을 분석해줘.`
- `2026-09-11 개선안 적용 전후의 완료율과 부정 피드백 변화를 비교해줘.`

### 5.1 같은 질문에서 탐색 테이블 확대

기준 구간의 날짜와 질문을 고정하고 Source 선택만 변경해 새 Run을 실행합니다.
Source 선택은 탐색을 허용하는 범위입니다. 에이전트가 실제 사용한 Source와 완료된
분석 근거를 결과에서 확인해야 합니다.

| 사례 | 질문 | 제한 탐색 | 추가 Source | 원시 데이터의 기대 결과 |
| --- | --- | --- | --- | --- |
| 부가서비스 | `부가서비스 메뉴를 찾느라 반복 탐색한 고객 중 검색이나 상담에 나타나지 않은 고객도 찾아줘.` | 검색, 상담 | 앱 행동, 부가서비스 가입 | 제한 탐색에서 판단 불가, 확장 후 조용한 탐색 고객 160명과 그중 미도달 16명 |
| 소액결제 | `소액결제 한도 변경이 끝나지 않은 고객의 반복 시도 단계와 이용 특성을 분석해줘.` | 검색, 상담 | 앱 행동, 고객 빌링 | 상담만으로 미완료 전체 규모 판단 불가, 확장 후 미완료 210명, 567회 시도와 완료 대조군 90명 |
| 로밍 | `로밍 요금제를 알아본 고객의 가입 여정과 개선 기회를 찾아줘.` | 검색, 상담 | 앱 행동, 로밍 이용 | 상담 가입 70명 중 앱에서 비교 후 이탈한 56명과 바로 상담을 요청한 14명 구분 |

표의 검색과 상담은 각각 `hackathon_search_history`, `hackathon_voc`입니다. 추가
Source는 `hackathon_app_behavior`, `hackathon_vas_subscription`,
`hackathon_billing_profile`, `hackathon_roaming_usage`를 뜻합니다.

부가서비스 검색 증가의 원인을 해석할 때는 같은 기간과 다음 질문을 고정하고
`hackathon_crm_campaign`을 마지막에 추가합니다.

> `부가서비스 관련 검색이 증가한 배경과 고객의 실제 의도를 찾아, 추적할 시그널을 제안해줘.`

CRM 추가 전에는 반복 검색과 상담, 앱 메뉴 행동만 관측되므로 해지나 메뉴 문제를 원인으로
확정할 수 없습니다. CRM 추가 후에는 9월 7일 구글 원 옵션 변경 안내를 받은 240명 중
160명(66.7%)이 발송 이후 변경 의도로 검색했고, 비수신 100명 중 검색 고객은 20명(20.0%)임을
연결할 수 있습니다. 수신군 검색률은 비수신군의 3.33배이며, 전체 부가서비스 검색 고객
180명 중 160명(88.9%)이 안내 수신자입니다. 따라서 1차 시그널 후보는 `구글 원 옵션 변경
안내 수신자의 변경 의도 검색률`이고, 반복 검색 실패율은 응답 적합성을 살피는 보조 지표입니다.

기존 두 테이블에서도 검색 반복과 상담 전환은 보입니다. 여기서 검증하는 차이는
두 테이블에 없는 고객이나 업무 상태까지 확인할 수 있는지입니다. 제한 탐색 결과는
`문제 없음`이나 `0명`으로 단정하지 않고 `현재 Source로 판단 불가`로 해석해야 합니다.

로밍은 네 Source를 허용한 Run에서 앱 이탈, 상담 가입과 로밍 상품 등록을 실제로
연결했는지 확인합니다.
같은 질문으로 개선 구간을 조회하면 대상은 28명입니다. 전후 고객은 서로 다른 합성
고객이므로 주간 비율 40%에서 20%로 비교합니다. 마지막 날 비율은 5%입니다.

더 자세한 확인이 필요할 때는 `앱에서 로밍 요금제 3개를 비교하다 가입 없이 나간 뒤
상담사에게 가입한 고객을 찾아줘. 바로 상담을 요청한 고객과 구분하고 실제 가입 기록도
확인해줘.`를 사용합니다.
이 질문은 탐지 조건을 공개하는 재현 확인용입니다.

Source를 많이 선택하면 실행 예산에 도달할 수 있습니다. 각 사례에 필요한 Source를
선택하고 `scan_complete`와 결과의 탐색 범위를 확인합니다. 아래 과거 Gemini Run의
매칭 수는 새 기간과 확장 사례의 보장값으로 사용하지 않습니다.

## 6. 검증 기록

### 6.1 2026-09-10 데이터 검증

`make seed-hackathon`으로 8개 원시 CSV, 총 15,617행과 8개 Source를 생성합니다.
생성 검증은 스키마, 날짜 범위, 식별자, 참조 무결성, 시간 순서, CRM 캠페인, 기존 코호트,
확장 탐색 사례, 노출률, 대조군 유지, 추세와 목표 범위를 확인합니다.

자동 테스트는 등록된 Source에서 앱 이탈과 상담 가입, 활성 로밍 상품을 연결했을 때
기준 구간 대상 56명이 유지되는지 확인합니다. 실제 탐색 도구의 `analyze_event_sequences`로도
요금제 비교 3회, 앱 이탈, 상담사 가입 처리와 상품 등록의 순서를 검증합니다. 새 로밍 사례의 Gemini 보고서 생성과
브라우저 실행은 아직 실검증하지 않았습니다.

## 7. 해석 제한

이 데이터는 합성 데이터이며 실제 고객이나 실제 통신 지표를 포함하지 않습니다. 발표에서는
`개선안 적용 후 지표가 함께 개선됐다`고 설명합니다. 이 데이터만으로 개선안이 변화의
원인임을 입증했다고 설명하지 않습니다. `CONTROL`, `VAS_AI_CTA_V1`,
`PAYMENT_CONSENT_V1`, `ROAMING_PLAN_GUIDE_V1`의 차이는 데모에서 날짜 효과와 개선안 노출을 구분하기 위한
장치입니다.

로밍 월 집계는 출국일 21시까지의 누적 스냅샷입니다. 그 시점의 사용량 0을 월 전체의
미사용으로 해석하지 않습니다. `DATA_USAG`의 byte 단위는 이 합성 데이터의 규약입니다.
제공받은 스키마에서 잘린 물리명은 추측해 추가하지 않았습니다.
