# 탐색 범위 확장 시연의 데이터 가능 범위

확인일: 2026-09-10

부가서비스는 검색과 상담에 없는 고객 여정을 앱 행동 추가 후 발견하는 시연이 가능합니다.
소액결제도 추가 고객과 재시도 경로를 발견할 수 있지만, 현재 데이터는 메뉴 탐색보다
한도 변경 절차의 중단을 보여줍니다. 정상 탐색과의 구분이나 고객의 의도까지 확정하는 데는
아래 제한사항이 있습니다. 이번 확인에서는 코드와 시딩 데이터를 변경하지 않았습니다.

## 확인 조건

- 분석 요청: `최근 일주일간 앱에서 원하는 문제를 해결하기 위해 곧바로 못 찾고 헤맨 고객 찾아줘`
- 고정 분석 구간: `2026-09-04` 이상, `2026-09-11` 미만, 한국 시간 기준
- 제한 공간: `hackathon_search_history`, `hackathon_voc`
- 확장 공간: 기존 공간에 앱 행동과 사례별 업무 테이블을 외부에서 추가
- 판단 대상: 헤맨 뒤 해결한 고객과 해결하지 못한 고객 모두 포함
- 결과 구분: 메뉴 도달, 업무 완료, 완료 여부 미확인을 별도 판단

범위 확장은 FE 등 외부에서 데이터 공간에 데이터를 추가하는 동작입니다.
조사 에이전트는 현재 제공된 공간 안에서 목표에 필요한 모든 데이터를 탐색할 수 있어야 합니다.
테이블 선택과 고객 연결을 기존 에이전트 진입점이나 사례별 고정 테이블 목록에 종속시키지 않습니다.
FE 구현은 현재 작업 범위에 포함하지 않습니다.

## 사례별 확인 결과

| 사례 | 제한 공간에서 보이는 내용 | 데이터 추가 후 확인한 내용 | 시연 판단 |
| --- | --- | --- | --- |
| 부가서비스 | 검색 고객 180명, 상담 고객 61명과 메뉴 위치 문의 | 검색과 상담에 없는 반복 메뉴 탐색 고객 160명, 그중 목표 메뉴 도달 144명과 미도달 16명 | 추가 여정 발견 가능, 일부 고객의 의도와 정상 탐색 구분은 미확정 |
| 소액결제 | 검색 고객 150명, 상담 고객 74명과 변경 실패 문의 | 앱 미완료 고객 210명 중 검색과 상담에 없는 60명, 미완료 고객의 시도 567회와 앱 완료 대조군 90명 | 절차 중단과 재시도 조사 가능, 메뉴를 못 찾는 헤맴의 직접 사례로는 부족 |

두 사례 모두 제한 공간에서 이미 일부 문제 징후가 보입니다.
시연에서는 데이터 추가로 새롭게 발견한 고객과 경로를 비교해야 합니다.
특정 테이블이 없는 상태의 미관측은 해당 행동이 없었다는 증거가 아닙니다.

### 부가서비스

원시 앱 CSV를 고객과 세션별로 묶고 `LOG_DTTM` 순서로 정렬했습니다.
기준 구간의 `menu_view` 세션은 340명이며, 모두 `마이`에 세 번 방문하는 반복 경로입니다.
이 확인의 코호트 선택에는 `vas_wandering`과 `vas_unreachable` 라벨을 사용하지 않았습니다.

실제 경로는 다음과 같습니다.

```text
도달: 마이 → 요금제 조회/변경 → 마이 → 멤버십 → 마이 → 가입정보 → 부가서비스 조회/해지
미도달: 홈 → 전체메뉴 → 마이 → 요금제 조회/변경 → 마이 → 데이터 충전 → 마이 → 전체메뉴
```

340명의 고객번호와 같은 기간의 검색, 상담 연결키를 비교하면 160명이 두 테이블에 없습니다.
이 중 144명은 부가서비스 메뉴 도달 기록이 있고 16명은 해당 메뉴 방문이 없습니다.
`hackathon_vas_subscription`을 추가하면 160명 모두 가입 상품 3개가 있음을 확인할 수 있습니다.

제한사항은 다음과 같습니다.

- 16명은 검색어, 상담 내용, 목표 메뉴 도달 기록이 모두 없어 부가서비스가 목적이었다고 확정하기 어려움
- 가입 상품 3개라는 사실만으로 조회나 해지 의도를 입증할 수 없음
- 144명의 메뉴 도달은 조회나 해지 업무 완료와 구분 필요
- 기준 주간의 부가서비스 앱 고객은 모두 반복 경로이며, 같은 목적의 직접 도달과 정상 비교 탐색 대조군 부족
- 개선 주간의 직접 도달 고객을 기준 주간 분석에 섞으면 관측 기간 조건 위반

추가 시딩이 필요하다면 같은 기준 주간에 직접 도달, 정상적인 다중 메뉴 탐색,
헤맨 뒤 도달하는 경로를 함께 넣어야 합니다. 미도달 고객의 의도를 확인하려면
진입 링크의 목적, 목적이 드러나는 버튼이나 화면 등 관측 가능한 단서가 필요합니다.
분석 정답을 뜻하는 라벨을 추가하는 방식은 적합하지 않습니다.

### 소액결제

`limit_page_entered`가 있는 고객 300명을 모으고 `limit_change_completed`의 존재를 확인했습니다.
앱 완료 고객은 90명이며, 앱 완료가 관측되지 않은 고객은 210명입니다.
210명 중 검색과 상담 어느 쪽에도 없는 고객은 60명입니다.

미완료 고객의 서로 다른 세션은 567개로, 고객당 평균 2.7회 시도입니다.
동의창 닫기로 끝나는 세션은 465개, 인증 실패로 끝나는 세션은 102개입니다.
상담에 나타나는 74명에게는 상담원이 한도 변경을 처리했다는 기록이 있습니다.
따라서 앱 미완료 210명 전체를 최종 미해결로 표시하면 안 됩니다.
상담 처리 기록과 독립된 업무 완료 증거도 구분해야 합니다.

`hackathon_billing_profile`에서는 앱 미완료 210명의 소액결제 이용 금액이 양수이고
앱 완료 90명은 0인 차이를 확인할 수 있습니다. 이는 합성 코호트의 특성이며 원인 증거는 아닙니다.
`SMLS_STLM_AMT`는 이용 금액으로, 현재 결제 한도나 변경 완료 상태가 아닙니다.

현재 앱 경로는 한도 변경 화면 진입부터 시작합니다.
메인, GNB, 다른 메뉴를 거쳐 목표 화면을 찾는 과정은 없습니다.
현재 질문에 엄격하게 맞추려면 정상적인 진입 경로와 헤매는 진입 경로를 추가로 시딩해야 합니다.
절차 중단까지 분석 목표에 포함하는지는 별도 설계 결정입니다.

## 공통 제한사항

| 제한 | 현재 확인한 상태 | 추가 설계나 시딩 시 필요한 내용 |
| --- | --- | --- |
| 상세 조작 누락 | 명시적인 스크롤, GNB 클릭, 검색창 클릭 이벤트 부재 | 세부 조작을 시연할 경우 행동 이벤트와 화면, 버튼 식별자 추가 |
| 정답성 라벨 노출 | 앱 Source의 `topic`과 `outcome`에 `vas_wandering`, `vas_unreachable`, `payment_incomplete` 등이 매핑됨 | 자율 발견 검증 시 평가용 정답과 에이전트 입력을 분리하고 실제 행동 순서로 판단 |
| 단조로운 경로 | 부가서비스 기준 구간은 두 메뉴 경로와 일부 즐겨찾기 동작으로 구성 | 같은 목적의 정상 탐색, 정상 비교, 우회 탐색을 함께 검증할 데이터 |
| 시간 기준 차이 | 앱 Source는 `BQ_LOAD_DTTM`, 검색은 `CREATED_AT`을 사용 | 여정 연결에 발생 시간과 적재 시간을 구분하는 계약 필요 |
| 신규 테이블 반영 | 현재 API 구성은 시작 시 온보딩 Source를 로드 | 새 배선에서 데이터 추가 후 다음 분석이 갱신된 공간을 읽는 동작 검증 |
| 자율 탐색 미검증 | 이번 확인은 CSV 집계와 기존 시딩 테스트 | 확정된 사용자 질문으로 실제 모델이 테이블과 패턴을 발견하는 별도 실행 |

KPI, 평가 rubric, 이 보고서의 정답 수치는 에이전트 분석 입력으로 사용하지 않습니다.
에이전트의 모든 데이터 탐색 권한은 제공된 분석 공간에 적용하며, 평가 자료는 그 공간에 포함하지 않습니다.

## 검증 기록

생성기와 내보내기 매핑을 읽고, 현재 저장된 원시 CSV를 직접 집계했습니다.
앱 세션은 `SESN_ID`로 묶어 `LOG_DTTM`으로 정렬하고 `CUST_NO`로 고객을 집계했습니다.
검색과 상담의 `CZ_LNK_KEY`를 앱 고객번호와 비교했습니다.
현재 합성 데이터에서 두 키의 값이 같다는 계약을 사용하며, 실제 데이터에 이를 일반화하지 않습니다.

다음 기존 테스트를 실행해 5개 통과, 17개 제외를 확인했습니다.

```bash
uv run --project backend pytest backend/tests/test_hackathon_seeding.py -q \
  -k 'vas_baseline or vas_two_sources or payment_baseline'
```
