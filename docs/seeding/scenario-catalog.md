# 9월 2주 시딩 시나리오 명세

수정일: 2026-09-09

현재 생성기는 2026-09-04~2026-09-17의 14일을 다룹니다. 9월 11일 09시에 개선을
시작하며, 기준 구간과 개선 구간은 각각 7일입니다. [기존 기획 메모](./seeding-plan.md)의
부가서비스와 소액결제 사례를 유지하고 로밍 사례를 추가합니다.

이 문서와 [실행 안내](./hackathon-2week-runbook.md)가 현재 데이터의 실행 명세입니다.
[초기 설계](../superpowers/specs/2026-08-31-hackathon-two-week-seeding-design.md)의
8월 기간과 6개 테이블 구성은 초기 버전 기록입니다.

## 1. 탐색 범위에 따른 검증 목적

해피케이스는 에이전트가 문제 패턴과 근거를 찾아 개선안을 제안하는 데모 성공 사례입니다.
고객 여정 자체에는 실패가 포함됩니다. 제한 탐색은 검색과 상담 두 테이블을 허용하고,
확장 탐색은 같은 날짜와 질문에 앱 행동과 사례별 업무 테이블을 추가합니다.

| 사례 | 두 테이블에 보이는 사실 | 확장 탐색에서 추가로 보이는 사실 |
| --- | --- | --- |
| 부가서비스 | 반복 검색, 메뉴 위치 문의와 상담 전환 | 검색과 상담에 없는 탐색 고객, 미도달, 즐겨찾기 직전 경로, 가입 서비스 수 |
| 소액결제 | 한도 변경 실패 문의와 상담 내용 | 고객별 실제 재시도 횟수, 동의 단계와 인증 단계 구분, 정상 완료 대조군, 이용 금액 |
| 로밍 | 정상 검색과 상담사의 요금제 가입 처리 | 앱에서 요금제 비교 후 이탈한 경로, 상담 가입과 실제 가입 기록의 연결 |

두 테이블에서 원래의 검색 실패 패턴까지 사라지도록 기존 데이터를 지우지는 않습니다.
같은 문제를 겪어도 검색이나 상담에 나타나지 않은 고객을 찾아내는 것이 확장 비교의
목적입니다. 로밍은 앱 탐색 후 이탈한 고객과 바로 상담을 요청한 대조군의 검색 내용,
상태, 횟수와 상담 요약을 같게 구성했습니다. 두 테이블만으로 앱 이탈 여부를 구분할 수 없습니다.

## 2. 기존 사례와 확장 탐색

### 부가서비스 조회/해지 탐색 실패

| 기준 구간 지표 | 고객 수 |
| --- | ---: |
| 메뉴 탐색 고객 | 340명 |
| 탐색 후 즐겨찾기 | 84명 |
| 메뉴 미도달 이탈 | 97명 |
| 상담 전환 | 61명 |
| 검색과 상담 모두에 없는 탐색 고객 | 160명 |
| 위 160명 중 메뉴 미도달 | 16명 |

앱 행동의 고객번호를 검색과 상담의 연결키와 비교하면 조용한 탐색 고객 160명을
확인할 수 있습니다. 이들은 부가서비스 가입 테이블에서 각각 3개 상품을 가집니다.
`hackathon_app_behavior`와 `hackathon_vas_subscription`을 추가해 오답 메뉴 이동,
상위 메뉴 복귀와 가입 서비스를 확인합니다. 장기 가입 여부까지 확인하려면
`hackathon_billing_profile`도 추가합니다.

개선안은 부가서비스 메뉴의 검색 CTA와 추천 질문입니다. `VAS_AI_CTA_V1` 노출 후
직접 도달률, 미도달률과 검색, 상담 지표를 비교합니다.

### 소액결제 한도 변경 중도 이탈

기준 구간은 미완료 210명, 시도 567회, 평균 2.7회이며 정상 완료 대조군은 90명입니다.
미완료 세션 중 동의 바텀시트 닫기는 465회로 약 82%입니다. 상담 전환 고객은 74명입니다.

`hackathon_app_behavior`를 추가해 동의 단계 이탈과 인증 실패를 구분합니다.
`hackathon_billing_profile`을 추가하면 미완료 210명의 소액결제 이용 금액이 양수이고
정상 완료 대조군 90명은 0이라는 차이를 확인할 수 있습니다. `SMLS_STLM_AMT`는
금액이며 현재 한도를 뜻하지 않습니다. 150,000원 한도는 앱 이벤트 라벨에 표현합니다.

개선안은 동의 절차 사전 안내와 선택값 보존입니다. `PAYMENT_CONSENT_V1` 노출 후
완료율과 동의 단계 이탈을 비교합니다. 로그만으로 UI가 실패의 원인이라고 단정하지 않습니다.

## 3. 추가 사례: 로밍 요금제 탐색 후 상담 가입

### 고객 상황과 선정 이유

고객은 로밍 요금제를 검색한 뒤 앱에서 4GB, 8GB, 12GB 요금제 상세를 비교합니다.
일부 고객은 앱에서 가입을 완료하지 않고 나간 뒤 상담사에게 요금제 안내와 가입을
요청합니다. 상담사는 가입을 처리하고 같은 고객, 가입번호의 로밍 상품 등록 기록이
남습니다. 모든 상품은 출국 당일 시작하며 시작일 지연을 가정하지 않습니다.

에이전트는 요금제 비교 후 이탈한 고객과 상담사가 가입을 완료한 고객을 연결해
앱의 비교 안내와 가입 동선을 개선할 기회를 제안합니다. 개선안은 데이터 제공량과 가격의
비교 안내, 선택한 요금제의 가입 CTA입니다. `ROAMING_PLAN_GUIDE_V1` 노출 후
앱에서 가입을 마치는 고객이 늘고, 탐색 후 이탈해 상담 가입으로 이어지는 비율이 줄어듭니다.
고객이 상담 채널을 선호했을 가능성도 있으므로 앱 결함이 원인이라고 단정하지 않습니다.

### 테이블과 탐지 조건

| Source | 원시 필드 | 확인할 내용 |
| --- | --- | --- |
| `hackathon_search_history` | `SEARCH_QUERY`, `STATUS`, `SEARCH_QUERY_TYPE` | `로밍 요금제 추천`, `completed`, `initial` 1회 |
| `hackathon_app_behavior` | `CUST_NO`, `ENTR_NO`, `SESN_ID`, `EVET_ACT_NM`, `REP_CHNL_MENU_NM` | 서로 다른 요금제 상세 3개 조회 후 가입 없이 이탈 |
| `hackathon_voc` | `CUST_NO`, `ENTR_NO`, `CALL_CRTE_DTTM`, `CSLR_PRSS_CNTN` | 앱 이탈 이후 상담사의 로밍 가입 처리 완료 |
| `hackathon_roaming_usage` | `CUST_NO`, `ENTR_NO`, `SPPS_CD`, `SPPS_ENTR_STUS_CD`, `SPPS_FRST_ENTR_DT` | 같은 고객과 가입번호의 실제 상품 가입 상태와 가입일 |

탐지 대상은 다음 조건을 모두 만족하는 고객입니다.

1. 같은 앱 세션에서 서로 다른 요금제 상세 3개를 조회한 후 `roaming_plan_selection_exited`로 이탈
2. 이탈 후 상담 이력에 `상담원 로밍 가입 처리 완료` 기록
3. 상담 당일 로밍 스냅샷에 같은 고객번호와 가입번호의 활성 상품 등록, `SPPS_ENTR_STUS_CD = A`

상담 요약에는 앱에서 나왔다는 정답을 넣지 않습니다. 검색과 상담만으로는 바로 상담을
요청한 고객과 구분할 수 없으며 앱 경로를 추가해야 합니다. 로밍 테이블은 상담 기록에
대응하는 실제 상품 가입 상태를 확인하는 근거입니다. Source의 상담 처리 dimension은
`resolution`이며, 상품 가입 상태는 로밍 Source의 `outcome`입니다.

### 규모와 대조군

| 구간 | 전체 고객 | 탐색 후 이탈하고 상담 가입한 고객 | 비율 |
| --- | ---: | ---: | ---: |
| 2026-09-04~2026-09-10 | 140명 | 56명 | 40% |
| 2026-09-11~2026-09-17 | 140명 | 28명 | 20% |
| 2026-09-17 하루 | 20명 | 1명 | 5% |

매일 서로 다른 고객 20명을 생성합니다. 기준 구간 대상은 하루 8명이고 개선 구간은
하루 7명, 6명, 5명, 4명, 3명, 2명, 1명입니다. 다음 대조군을 매일 포함합니다.

- 요금제를 길게 비교하거나 이탈하지 않고 바로 상담 가입을 요청한 고객 2명
- 요금제 상세 3개를 비교한 뒤 앱에서 가입을 마친 고객 2명
- 요금제 상세 1개를 보고 앱에서 가입을 마친 나머지 고객

상담 가입은 기준 구간 70명, 개선 구간 42명입니다. 각 구간에서 바로 상담을 요청한
14명을 제외해야 앱 탐색 후 이탈한 대상 56명과 28명이 됩니다. 요금제 비교나 상담
가입만으로 대상 전체를 판단할 수 없습니다. 사용량 0은 실패 조건으로 사용하지 않습니다.

개선 구간의 목표 노출률은 20%, 35%, 50%, 65%, 80%, 90%, 100%입니다.
노출 고객 수를 정수로 반올림하므로 실제 일별 비율에는 작은 차이가 있습니다.
최종일에는 전원이 노출되므로 마지막 날의 동시 대조군은 없습니다.

## 4. 스키마와 시간 해석

로밍은 제공된 `L1DA_RMNG_USE_MMLY_INTG_H`의 물리명이 완전히 확인되는 필드만
사용합니다. `ALL_VCE_PHCL_U...`, `LAST_RMNG_PP...`처럼 잘린 물리명은 추측하지 않습니다.

- 월 파티션 `P_YYYYMM`: 정수 `202609`
- 원시 로밍 연결키: `CSZ_LNK_KEY`, 다른 테이블의 `CZ_LNK_KEY`와 철자 구분
- Source 고객 연결: `synthetic_customer` namespace의 `CUST_NO`
- 가입과 청구계정 연결: `ENTR_NO`, `BILL_ACNT_NO`
- 날짜 문자열: `YYYYMMDD`, 미귀국과 미과금은 빈 문자열, 종료 미정은 `99991231`
- 데이터 사용량 단위: 이 합성 데이터에서 byte로 정의

월별 테이블의 행은 출국일 21시 적재 시점까지의 누적 스냅샷입니다. 9월 말의 확정
사용량을 앞선 날짜로 옮기지 않습니다. 상품 가입일과 시작일은 모두 출국 당일입니다.
상담 가입은 앱 이탈 이후 14시대에 처리하고 21시 로밍 스냅샷에서 등록 상태를 확인합니다.
출국일 이후 귀국 여부는 미관측입니다.

업무상 과거 가입일과 `99991231` 같은 종료 미정 값은
14일 이벤트 범위 제한의 대상이 아닙니다. 이벤트 발생일, 적재일과 월 파티션은 새 기간에
맞춥니다. 빌링 프로필도 각 고객의 관측일에 적재해 기준 구간에서 조회할 수 있게 합니다.

## 5. 결과물과 검증 경계

`data/seeding/hackathon-2week/`에는 7개 CSV와 시스템 등록용 복사본이 있습니다.
로밍은 280행이며 전체 원시 행 수는 15,377개입니다. `daily_kpis.csv`의
`roaming_browse_exit_agent_signup_count`, `roaming_browse_exit_agent_signup_rate`,
`roaming_usage_rate`는 원시 데이터에서 계산한 발표와 검증용 지표입니다.

테스트는 제한 탐색의 관측이 같다는 점, 확장 탐색의 고객 수, 날짜와 참조 무결성,
등록 후 필드 노출과 CSV 재현성을 확인합니다. 실제 탐색 도구의 순서 분석으로도 앱
요금제 비교, 앱 이탈, 상담 가입과 로밍 상품 등록을 연결해 기준 구간 56명을 검증합니다.
KPI와 평가 rubric은 에이전트 입력에
넣지 않습니다. 실제 Gemini가 필요한 테이블을 선택해 완전한 보고서를 만드는지는
별도 실행에서 확인해야 합니다.
