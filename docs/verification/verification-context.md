# 검증 컨텍스트 분할 검증 기록

검증일: 2026-09-10

이 문서는 컨텍스트 분할 당시의 측정 기록입니다.
이후의 호출 수와 시간 개선은 [검증 모델 왕복 호출 감소](verification-latency.md)에 기록했습니다.

## 변경 범위

검증자마다 후보 하나와 그 후보의 SQL, 지표 정의만 전달하며 최대 6개를 동시에 실행합니다.
모든 승인된 원본 테이블은 정상 반례와 다른 소스의 근거를 확인할 때 계속 조회할 수 있습니다.

`recheck_candidate`는 검증자의 소유권으로 SQL을 재실행하고, 대표 여정을 조회하고,
지표를 독립 재측정합니다. 이 도구는 자동으로 판정을 내리지 않습니다.
검증 모델은 SQL 조건의 의미, 정상 비교군, 피드백의 고객과 의도, 시간 순서와 최종 해결 상태를 판단합니다.

검증자가 조회한 고객 집합은 작업 소유의 임시 테이블로 저장해 후속 SQL에서 재사용합니다.
다른 검증자는 해당 테이블을 조회할 수 없고, 저장할 시그널 정의에는 사용할 수 없습니다.
동적 SQL과 테이블 macro를 통한 소유권 우회도 차단합니다.

질의 결과는 서버에 전부 저장하고, 미리보기와 추가 페이지는 최대 20행씩 반환합니다.
96,000바이트 입력 한도에 가까워지면 이미 전달한 과거 결과와 호출 기록을 재조회 가능한 참조로 바꿉니다.
2,048바이트 이하의 짧은 집계표와 여정은 보존합니다.
이 한도는 고정 도구 스키마를 제외한 메시지 내용과 도구 인자의 UTF-8 크기이며, 정확한 토큰 한도는 아닙니다.

## 유지한 확정 조건

- 조사자와 다른 검증 작업이 직접 실행한 고객 집계와 근거 질의
- 검증자에게 실제 전달한 대표 고객 여정
- 최종 고객 집계와 일치하는 동일 정의의 독립 재측정
- 다른 후보에 배정된 검증 작업의 질의를 독립 근거로 인정하지 않는 소유권 검사
- 실패한 후보를 미확정으로 남기고, 먼저 완료한 후보를 보존하는 처리
- 전체 영향 고객 수를 서버에서 중복 제거하는 집계

최신 도구 호출 배치 전체는 모델이 읽기 전에 압축하지 않습니다.
조회 도구와 `finish`를 같은 응답에 제출하면 판정을 보류하고 조회 결과를 먼저 전달합니다.
묶음 조회의 일부가 실패해도 앞서 성공한 여정과 질의 결과를 응답에 남깁니다.

## 비교 방법

기준 실행은 `f9d10f57-5e90-4ee6-ac3d-1c2e175b42b3`입니다.
최근 일주일의 검색 실패, 앱 반복 탐색과 상담 전환을 조사한 합성 고객 780명의 후보 6개를 사용했습니다.
기준 실행의 후보, SQL과 지표 정의를 재생하고 검증 단계만 실제 Bedrock 모델로 실행했습니다.
조사와 보고 모델은 다시 호출하지 않았으며, 시그널을 등록하지 않았습니다.

검증 시간은 최초 검증 작업 시작부터 마지막 작업 종료까지의 시간입니다.
데이터 준비와 trace 전송 시간은 제외하고, 병렬 작업의 대기는 포함합니다.
비용은 Langfuse에 적재된 generation의 계산값이며 AWS 청구서 금액은 아닙니다.
모델별 단일 합성 사례 비교이므로 일반적인 품질이나 평균 지연을 보장하지 않습니다.

## 최종 실측

최종 실행은 `ff245ede-8e15-4baf-b045-cdac9a5aca74`이며 후보 6개 검증을 모두 마쳤습니다.
동일한 Opus 모델을 사용했고 최종 기본 동시 실행 수와 같은 6개로 측정했습니다.

| 지표 | 기존 검증 | 컨텍스트 분할 최종 |
| --- | ---: | ---: |
| 검증 단계 시간 | 400.632초 | 436.304초 |
| 단일 호출 최대 입력 토큰 | 178,822 | 38,386 |
| 전체 입력 토큰 합계 | 1,426,346 | 2,801,795 |

| 판정 | 6개 확정 | 4개 확정, 2개 미확정 |

최대 입력은 78.5% 줄었지만 검증 시간은 8.9% 늘었습니다.
컨텍스트 분할과 입력 상한 적용은 검증했으나, 응답 시간과 총비용 개선은 달성하지 못했습니다.
작은 작업별로 추가 근거를 확인하면서 모델 왕복 호출이 늘었고 마지막 후보의 검증이 전체 시간을 결정했습니다.
입력 상한은 전체 실행 토큰 예산을 제한하지 않습니다.

최종 검증은 소액결제 후보에 섞인 다른 고객군의 피드백 90건과
부가서비스 후보의 정상 비교군 84명이 실제로 모두 대상 고객군에 속한다는 오류를 찾았습니다.
로밍 상세 1회 후 상담 전환 후보는 반복 탐색 근거 부족으로 미확정 처리했습니다.
전체메뉴 반복 후보도 검색과 앱 사용의 시간 순서와 비교군 결과를 확인한 뒤 미확정 처리했습니다.
독립 조회와 재측정 조건은 유지했지만, 이 한 사례만으로 모델의 검증 능력이 전반적으로 같다고 단정할 수는 없습니다.
판정 이유에도 일부 원인 추정 표현이 남아 있어 인과관계 판단에는 추가 품질 평가가 필요합니다.

최종 코드에서 관련 Backend 테스트 139개와 Compose 테스트 5개를 통과했습니다.
이전 전체 관련 범위 실행은 153개를 통과했고, 마지막 소유권 방어와 동시 실행 수 변경 뒤 관련 139개를 다시 실행했습니다.
Ruff와 diff 검사도 통과했습니다. Backend 이미지를 다시 빌드하고 재시작한 뒤
앱, Backend health/Swagger, Langfuse health의 HTTP 200 응답을 확인했습니다.
실제 컨테이너의 검증 모델은 Opus, 동시 실행 수는 6, 입력 한도는 96,000바이트입니다.

## Haiku 선택 판단

`us.anthropic.claude-haiku-4-5-20251001-v1:0`의 Bedrock Converse 도구 응답을 확인했습니다.
연결 시험은 약 3.8초였으며, 후보 6개 검증은 약 241초, 계산 비용은 약 2.75달러였습니다.

하지만 상담 전환만으로 앱 정보가 부족하다고 단정했고,
검색의 `completed`를 실제 서비스 해지 완료로 해석하는 오류가 있었습니다.
이번 작업에서는 Haiku를 기본 검증자로 선택하지 않았습니다.
`BEDROCK_VERIFIER_MODEL`을 생략하면 기존 `BEDROCK_MODEL`을 사용합니다.
현재 로컬 검증 모델은 Opus 4.6이며 조사 모델은 Sonnet 4.6입니다.

## 재실행

통합 Compose 환경을 초기화한 뒤, 기존 합성 조사 Artifact가 있는 로컬에서 실행합니다.
이 명령은 실제 Bedrock 호출 비용을 발생시킵니다.

```sh
uv run --project backend python scripts/benchmark-verification.py \
  --artifacts .local/compose/evaluation-f9d10f57 \
  --model us.anthropic.claude-opus-4-6-v1 \
  --concurrency 6
```

`--concurrency`는 별도 벤치마크 프로세스에만 적용합니다.
결과와 공개 trace 통계는 `.local/compose/verifier-benchmark-<run_id>/`에 저장합니다.
환경 파일과 API Key는 출력하지 않습니다.
