# 시그널 빨리감기 검증

## 2026-09-11 데이터 경계와 시작일 복구

관측 데이터가 없거나 SQL 측정이 불가능하면 `blocked`로 멈추도록 변경했습니다.
마지막 성공 측정을 다음 분석일 기준으로 사용하며 실패한 날의 이력을 새로 저장하지 않습니다.
`POST /api/signals/fast-forward/reset`과 프론트의 `시작일 설정`을 추가했습니다.

| 검증 | 결과 |
| --- | --- |
| 구현 전 재현 | 백엔드 6개 실패, 프론트 2개 실패 |
| 백엔드 전체 테스트 | 1,035개 통과 |
| 최종 빨리감기, 일정, 알림 회귀 테스트 | 64개 통과 |

| TypeScript 타입 검사 | 통과 |

| PC와 모바일 Playwright | 경계와 재설정 2개, 기존 네이티브 알림 6개 통과 |
| 실행 중인 등록 시그널 2개 | 재설정 후 이틀 연속 성공, 모든 지표 값 존재 |

집중 테스트는 데이터 끝 중단, 중간 날짜 중단, 데이터 추가 후 재개, 빈 날짜의 0명 오인 방지,
재시작 시 정의와 알림 조건 유지, 새 알림 발생, 잠금 충돌, 프로세스 재생성 후 요청 재생,
트랜잭션 실패 시 이력과 보관 테이블의 원자적 복구를 확인했습니다.
재설정 전에 중단된 요청을 나중에 재시도해도 새 시작일을 덮어쓰지 않는 것을 추가 확인했습니다.
브라우저 테스트는 데이터가 끝난 주간 시그널을 등록하고 실제 SQL로 하루씩 측정했습니다.
시작일 재설정의 응답을 유실시킨 뒤 새로고침해도 같은 ID와 날짜로 복구됐습니다.
기존 네이티브 알림, 여러 탭의 중복 방지, 권한 차단 시 앱 안의 알림 수신도 PC와 모바일에서 통과했습니다.
최종 Docker Backend 재시작 후 기존 재설정 요청을 재전송해도 현재 날짜와 이력이 유지됐습니다.

로컬 Docker의 기존 두 시그널은 한국 시각 9월 11일부터 다시 시작했습니다.
기존 측정 8건과 6건은 `signal_tracking_archives`에 보관했고 선택한 알림 조건은 변경하지 않았습니다.
현재 활성 이력은 9월 10일의 비교 기준과 9월 11일, 12일의 성공 측정입니다.
다음 빨리감기는 9월 13일을 분석합니다.

| 시그널 | 9월 11일 | 9월 12일 |
| --- | --- | --- |
| 로밍 비교 후 상담 가입 대상 고객 수 | 7명 | 6명 |
| 로밍 요금제 추천 검색 대상 고객 수 | 20명 | 20명 |
| 검색 시그널 모집단 고객 수 | 96명 | 92명 |
| 검색 시그널 대상 고객 비율 | 20.83% | 21.74% |

실제 두 시그널은 선택한 알림 임계값을 새로 충족하지 않아 새 알림이 없었습니다.
알림 발생 경로는 별도 합성 시그널에 1명 이상 조건을 선택한 브라우저 테스트로 확인했습니다.
공개 집계 결과와 화면은 `data/live-validation/fast-forward-recovery/`에 저장했습니다.
재설정 전 전체 SQLite 백업은 Docker 데이터 볼륨의
`/app/data/recovery/fast-forward-20260911/before-reset.sqlite3`에 보관했습니다.

Starlette의 기존 TestClient 사용 중단 예고 경고가 있습니다. 브라우저 테스트의 별도 Backend는
로컬 3100번 포트의 Langfuse 수집기로 연결하지 못했지만 실제 SQL과 알림 검증에는 영향이 없었습니다.
Launcher와 관측 설정은 이번 변경 대상에 포함하지 않았습니다.

```sh
ONBOARDED_SOURCES_DIR="$PWD/data/seeding/hackathon-2week/onboarded-sources" \
SIGNAL_SCHEDULER_ENABLED=false E2E_BACKEND_PORT=38123 E2E_FRONTEND_PORT=33123 \
npm --prefix frontend run e2e -- signal-fast-forward-boundary.spec.ts
```

## 2026-09-10 최초 구현 검증 기록

2026-09-10에 등록 시그널의 다음 일자 SQL 분석, 기존 알림 폴링, 중복 방지와 재시작 복구를
검증했습니다. 신규 API는 `POST /api/signals/fast-forward`입니다.

| 검증 | 결과 |

| 신규 동작의 구현 전 실패 | 미구현 경로의 `405`와 Swagger 경로 누락 확인 |

| `git diff --check` | 통과 |

기존 Starlette의 httpx TestClient 사용 중단 예고 경고 1건이 있습니다.
저장소 루트에서 테스트 경로 없이 실행하면 백엔드의 `asyncio_mode=auto` 설정을 적용하지
못하므로, 전체 검증 명령은 `backend/tests`를 명시합니다.

신규 테스트는 실제 canonical event와 DuckDB를 사용합니다. 주간 분석의 후보를 등록하고
변화량 조건을 선택한 뒤 다음 하루를 측정합니다. 기준 대상 고객 1명과 다음 날 4명의 차이
3명이 기존 폴링 이벤트에 기록되며 이벤트의 기준 ID와 측정 ID가 실제 이력과 일치합니다.

다음 경계도 확인했습니다.

- 여러 날을 날짜순으로 실행하고 새 요청은 다음 날부터 시작
- 같은 UUID 재시도와 Backend 재생성 후 응답 일치
- 측정 저장 직후 중단되어도 예약한 날짜부터 복구, 측정과 이벤트 중복 없음
- 주간 측정과 같은 종료일의 하루 측정이 있을 때 하루 기준 우선
- 부분 일자 등록 후 다음 자정 정렬, 기준 측정의 알림 억제
- 자료 없는 미래 날짜를 분모 없는 고객 수 지표에서도 `unavailable`로 처리
- 비활성 시그널과 일정 제외, 없는 ID의 전체 요청 거절
- 일별 작업과 공유하는 잠금, 수동 측정 및 추적 상태 변경의 `409`
- 미래 일정의 역행 방지, 완료된 일별 실행 재사용
- 알림 조건 미선택, 임계 미충족, 동일 조건 유지와 재진입
- 한국어 summary와 `signals` 태그, 요청과 응답 OpenAPI 모델

## 실제 HTTP와 프로세스 재시작

다음 명령을 별도 포트 8021과 별도 임시 저장소에서 실행했습니다.

```sh
uv run --project backend python scripts/verify-signal-fast-forward-live.py
```

승인된 `hackathon_search_history` Source에서 부가서비스 반복 검색을 고정 SQL로 측정했습니다.
최초 주간 범위는 한국 시각 9월 4일 00:00부터 9월 11일 00:00까지입니다.
빨리감기 후에는 한국 시각 9월 11일 하루를 새로 분석했습니다.

| 항목 | 결과 |
| --- | --- |
| 빨리감기 측정 시간 | 1.782초, 이번 실행에서 측정 |
| 대상 고객 수 | 28명 |
| 모집단 고객 수 | 50명 |
| 대상 고객 비율 | 56% |
| 기존 폴링에서 받은 알림 | 1건 |
| 수동 측정과 비교 | 측정 ID와 지표 값 일치 |
| 브리핑 및 일별 이력 | 같은 측정 ID 확인 |
| 동일 요청 재전송 | 원래 응답과 일치 |
| 프로세스 종료 후 재시작 | 원래 응답과 이벤트 유지, 새 요청은 9월 12일 분석 |

검증용 조건은 사용자의 명시적 선택을 재현한 하루 대상 고객 수 1명 이상입니다.
추천 생성은 fixture 모드이며 새 LLM 분석은 실행하지 않았습니다.
SQL 분석과 이벤트 생성은 실제 경로를 사용했습니다. 이벤트를 직접 삽입하지 않았습니다.
원본 검증 결과는 무시된 `data/live-validation/signal-fast-forward/verification.json`에 저장했습니다.

## 검토에서 수정한 사항

1. 데이터가 없는 날짜에 분모 없는 SQL이 0명을 반환할 수 있어, 빨리감기에서 빈 관측 공간을
   측정 불가로 처리했습니다. 기존 일반 측정의 0명 계약은 유지했습니다.
2. 주간 스냅샷을 나중에 저장하면 같은 종료일의 하루 기준을 가릴 수 있어, 종료일이 같을 때
   하루 측정을 우선하도록 수정했습니다. 더 최근의 Source 버전 변경을 건너뛰지는 않습니다.
3. 과거 날짜 빨리감기가 정상 일정을 뒤로 이동시키지 않도록 다음 실행일의 최댓값을 저장합니다.

## 사용 범위

실제 Source에 다음 날짜 데이터가 있어야 합니다. 기본 해커톤 Source는 2026년 9월 17일까지이므로
처음부터 9월 18일 00:00까지 분석하면 다음 날짜는 측정할 수 없습니다.
알림을 받으려면 조건을 선택하고 기존 폴링을 유지해야 합니다. OS 알림 표시는 기존 브라우저
권한 정책을 따르며 이번 검증은 백엔드 이벤트와 폴링 응답까지 확인했습니다.
SDD 개인 원격 저장소는 `Repository not found`로 동기화에 실패했고 로컬 설계 및 계획은 저장했습니다.
