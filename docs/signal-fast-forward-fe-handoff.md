# 시그널 빨리감기 API 연결

시그널과 알림 조건을 저장한 뒤 `POST /api/signals/fast-forward`를 호출하면 다음 날짜의
Source 데이터로 실제 분석을 실행합니다. 기존 `GET /api/signal-alert-events` 폴링에서
임계값을 충족한 이벤트를 받습니다. 서버의 실제 시간은 바꾸지 않습니다.

## 호출

```http
POST /api/signals/fast-forward
Content-Type: application/json
```

```json
{
  "request_id": "087b96ae-cea7-4ec9-9c8c-d16b2dd4d967",
  "days": 1
}
```

버튼 클릭 한 번마다 `crypto.randomUUID()`로 새 ID를 만듭니다. 처리 중에는 버튼을 비활성화하고
오류나 응답 유실로 같은 클릭을 재시도할 때는 같은 ID와 입력을 사용합니다.
예시 UUID를 여러 독립 실행에 재사용하면 안 됩니다.

| 입력 | 의미 |
| --- | --- |
| `request_id` | 필수 UUID, 한 번의 빨리감기 식별자 |
| `days` | 기본 1, 1~7 사이 정수, 문자열과 Boolean 불가 |
| `signal_ids` | 선택 사항, 중복 없는 1~100개 ID, 생략 시 현재 등록 목록 전체 |

`paused`, `archived`, 일정의 `enabled=false`인 시그널은 건너뜁니다.
시그널별 마지막 분석 날짜가 다르면 각 시그널의 다음 날부터 분석합니다.
목록이 비어 있으면 `200`과 빈 `items`를 반환합니다.

## 날짜와 분석

마지막 측정의 `end_at`은 미포함 종료 시각입니다. 예를 들어 최초 질의가 한국 시각
9월 4일 00:00부터 9월 11일 00:00까지였다면 첫 빨리감기는 **9월 11일 하루**를 분석합니다.
응답의 UTC 범위는 `2026-09-10T15:00:00Z`부터 `2026-09-11T15:00:00Z`까지입니다.
두 번째 독립 요청은 9월 12일을 분석합니다. 자정이 아닌 시각에 끝난 질의는 다음 한국 시각
자정부터 시작하므로 처음의 부분 일자와 겹치지 않습니다.

주간 측정은 하루 변화량의 기준으로 사용할 수 없습니다. 따라서 직전 하루의 성공 측정이
없으면 같은 SQL로 그 하루를 먼저 측정합니다. 기준 측정은 이력에 저장하지만 알림을 평가하지
않습니다. 다음 하루부터 기존 사용자 선택 조건을 평가합니다. 같은 종료 시각의 주간 측정과
하루 측정이 함께 있으면 하루 측정을 비교 기준으로 우선합니다.

고정 SQL의 재측정에는 새 LLM 호출이 필요하지 않습니다. 최초 분석에서 등록한 정의,
Source 범위, 기본 지표와 사용자 정의 지표를 그대로 사용합니다.
일별 실행은 기존 `/daily-results`와 `/measurements`에 나타납니다.
자동 측정 일정은 기존 일정과 빨리감기 마지막 날의 다음 실행일 중 늦은 시각으로 전진합니다.

## 응답과 폴링

HTTP `200`은 요청 처리가 끝났다는 뜻입니다. 개별 측정의 성공은
`items[].daily_results[].measurement.status`로 확인합니다.

| 필드 | 의미 |
| --- | --- |
| `request_id`, `days`, `timezone` | 실행 식별자, 요청 일수, `Asia/Seoul` |
| `items[].signal_id` | 처리한 시그널 |
| `items[].status` | `completed` 또는 `skipped` |
| `items[].reason` | 건너뛴 사유 |
| `items[].start_at`, `end_at` | 이번 요청의 고정된 분석 범위 |
| `items[].baseline_measurement` | 직전 하루의 측정, 실패 시 `status=unavailable` |
| `items[].daily_results` | 날짜 오름차순 기존 `DailyResult` 모델 |
| `items[].alert_events` | 측정 ID에 연결된 기존 `AlertEvent` 모델 |

응답을 받은 뒤 브리핑, 시그널 상세의 이력과 비교 데이터를 다시 조회합니다.
알림은 **기존 폴링에서 표시**합니다. 응답의 `alert_events`에서도 별도로 알림을 표시하면
중복될 수 있습니다. 직접 반영해야 한다면 기존 폴링과 `event_id` 중복 제거 상태를 공유해야 합니다.
빨리감기 호출 전부터 폴링을 유지하며 커서를 초기화하거나 최신 커서로 건너뛰지 않습니다.

API는 측정 완료까지 기다리는 동기 요청입니다. 여러 시그널이나 여러 날이면 응답 시간이
늘어나므로 처리 중 상태를 표시합니다. 응답을 받지 못했어도 서버 실행은 계속될 수 있습니다.
같은 ID의 완료 응답은 Backend 재시작 후에도 그대로 반환합니다.
중간에 Backend가 종료되면 같은 ID 재요청으로 저장된 날짜와 일별 실행에서 재개합니다.

## 알림이 없는 경우

- 사용자가 알림 조건을 선택하지 않은 경우
- 실제 값이 임계값에 진입하지 않았거나 계속 같은 조건을 충족하고 있는 경우
- 다음 날짜의 데이터가 없어 `measurement.status=unavailable`인 경우
- 변화량의 기준 측정이 없거나 Source 버전과 지표 단위가 달라 비교할 수 없는 경우
- 상대 변화율 기준값이 0인 경우
- 시그널이 일시 중지, 보관 상태이거나 일정이 비활성화된 경우

빨리감기는 원본 데이터를 생성하거나 날짜만 바꿔 복제하지 않습니다. 연결된 Source에
다음 날짜의 관측값이 있어야 합니다. 이 프로젝트의 기본 해커톤 Source는 2026년 9월 17일까지
데이터가 있으므로, 다음 일자 데모를 보려면 최초 분석 종료를 9월 11일 00:00 등으로 설정합니다.
9월 18일 00:00까지 전 기간을 처음부터 분석하면 그다음 날의 데이터는 없습니다.

자료 없는 날은 `unavailable` 이력으로 남기고 다음 날로 진행합니다. 같은 `request_id` 재전송은
이 결과를 재생합니다. 데이터를 나중에 적재했다면 기존 수동 `/measurements` API에 해당 하루를
보내 복구합니다. 앞선 날짜는 이후 알림 평가가 진행되기 전에 복구해야 변화 조건을 평가할 수 있습니다.

## 오류

| 코드 | 처리 |
| --- | --- |
| `404` | 요청에 없는 시그널 ID 포함, 측정 시작 전 전체 요청 거절 |
| `409` | 일정 잠금 사용 중이면 같은 입력과 ID로 재시도, ID 입력 충돌이면 원래 입력 확인 |
| `422` | UUID, 일수, 중복 ID, 알 수 없는 필드 등 요청 계약 오류 |
| `500` 또는 연결 유실 | 같은 입력과 ID로 재시도, 저장된 실행에서 재개 |

## 프론트 연결

첫 질의의 기본 기간은 한국 시각 2026년 9월 4일~10일입니다. 결과 화면에서
`변화 캐치 맡기기`로 알림 기준을 저장한 뒤, 등록 완료 화면 또는 상단 알림함의
`브라우저 알림 켜기`를 선택하고 브라우저 권한을 허용합니다.
상단 `하루 빨리감기`는 기본 기간 다음인 9월 11일부터 실제 측정을 실행합니다.
다음 클릭은 각 시그널의 다음 날짜를 분석합니다.

알림을 누르면 해당 시그널 상세가 열립니다. 브리핑과 열린 상세의 측정 이력도 다시 조회합니다.
빨리감기 응답이 유실되면 `같은 요청 재시도`를 선택합니다. 요청 ID는 같은 탭의
`sessionStorage`에 저장하므로 새로고침 후에도 같은 날짜의 응답을 복구합니다.

네이티브 알림은 서비스 워커의 `showNotification()`을 사용합니다.
여러 탭은 Web Locks와 `localStorage`의 이벤트 순번으로 중복 표시를 방지합니다.
알림 표시 실패와 권한 거절은 기존 폴링 커서와 앱 안의 알림함을 멈추지 않습니다.

**현재 알림 수신 범위는 앱이 열린 동안입니다.** 보이는 탭은 5초, 숨겨진 탭은 15초
간격으로 폴링하며 빨리감기 완료 직후에도 조회합니다. 모든 탭이 닫힌 뒤 발생한 이벤트를
서버에서 전송하는 Web Push는 포함하지 않습니다. 이미 표시된 알림에서 앱을 다시 여는
경로는 `/?signal=<signal_id>`입니다.

HTTPS 또는 localhost 계열의 보안 컨텍스트와 알림 권한이 필요합니다. 브라우저에서
권한을 허용해도 운영체제의 알림 차단이나 집중 모드에 따라 배너가 표시되지 않을 수 있습니다.
차단된 권한은 주소창 사이트 설정에서 변경합니다. 지원하지 않는 환경에서는 앱 안의
알림함을 사용합니다. API 사용 조건은 [MDN 알림 문서](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerRegistration/showNotification)에서 확인할 수 있습니다.

## 자동 검증

```sh
uv run --project backend python scripts/verify-signal-fast-forward-live.py
```

별도 포트 8021과 임시 저장소에서 합성 Source의 주간 SQL, 다음 하루 SQL, 기존 이벤트 폴링,
수동 측정과의 결과 일치, 프로세스 재시작과 다음 요청의 날짜 전진을 검증합니다.
추천은 fixture 모드를 사용하며 기존 등록 시그널이나 조건을 수정하지 않습니다.

```sh
ONBOARDED_SOURCES_DIR="$PWD/data/investigation-demo-sources" \
SIGNAL_SCHEDULER_ENABLED=false \
E2E_BACKEND_PORT=38121 E2E_FRONTEND_PORT=33121 \
npm --prefix frontend run e2e -- signal-notifications.spec.ts
```

브라우저 검증은 별도 Backend 저장소와 Next 출력 폴더를 사용합니다. 최초 Run은 실제
fixture API로 실행합니다. fixture planner에 SQL 후보 제안 기능이 없으므로 완료된 Run에
같은 기간의 실제 SQL로 측정한 후보만 추가합니다. 이후 화면 등록, 조건 저장, 빨리감기,
SQL 측정과 알림은 실제 구현을 사용합니다. 네이티브 알림 메서드도 대체하지 않습니다.
테스트는 전체 Chromium의 headless 모드를 사용합니다.
기본 Headless Shell과의 차이는 [Playwright 브라우저 문서](https://playwright.dev/docs/browsers#chromium-new-headless-mode)에 설명되어 있습니다.
