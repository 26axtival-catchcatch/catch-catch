# 01. 제품·UX 기획안

이 화면들이 **왜 이 모양인지**를 담습니다. 화면을 새로 만들거나 고칠 때 판단 기준이
되는 문서이므로, 구현 지시만 필요하더라도 먼저 읽어야 합니다.

---

## 1. 한 문장

> **고객이 말하기 전에 신호를 잡고, 무엇이 달라질지 예측하고, 맞았는지 채점한다.**

"물어보면 답해 주는 도구"가 **아닙니다.** 질의응답 도구로 보이는 순간 이 서비스는
사내에 이미 있는 BI 대시보드와 구분되지 않습니다.

서비스명은 **캐치캐치 (Customer Signal Catcher)** 이고 팀명은 **네박자** 입니다.
상단 바에 `PROTOTYPE by 네박자` 로 명시합니다.

---

## 2. 문제

고객은 의견을 남기기 전에 이미 행동으로 니즈를 표현합니다.

```
앱 메뉴 탐색 → AI검색에서 '일본 로밍' 반복 검색 → 로밍 상품 비교
             → 가입 직전 이탈 → 며칠 뒤 상담 채널에서 다시 문의
```

이 행동들은 검색·앱로그·가입·상담·피드백처럼 **서로 다른 시스템에 흩어져** 있어
하나의 시그널로 연결되지 않습니다. 담당자가 알고 싶은 것은 개별 이벤트가 아니라
"이 고객은 무엇을 해결하려 했나 / 비슷한 고객이 얼마나 되나 / 우리가 먼저 무엇을
제안할 수 있나" 입니다.

---

## 3. 사용자

| 역할 | 알고 싶은 것 |
| --- | --- |
| AI검색 기획자 (대표 페르소나) | 검색이 만족스럽지 않았던 고객은 그다음 무엇을 했나 |
| CX 담당자 | 채널을 넘나드는 고객 경험의 흐름 |
| 고객센터 운영 | 상담 전후의 고객 행동 |
| 디지털채널 기획 / 서비스 PO | 반복 탐색하거나 막히는 여정 |
| CRM / 마케팅 | 특정 니즈를 가진 고객군과 그들에게 할 제안 |

Mock 시나리오의 제안 카드(`SUGGESTIONS`)가 이 페르소나들을 그대로 태그로 답니다 —
`AI검색 기획`, `CX`, `CRM`.

---

## 4. 심사 배점이 설계를 결정한다

이 프로젝트는 해커톤 제출물입니다. 배점 전문은 `docs/judging-criteria.md`.

| 항목 | 배점 |
| --- | ---: |
| 문제 정의 / 독창성 | 25 |
| Agent 설계 / 자율성 | 15 |
| **완성도 / 신뢰성** | **30** |
| 업무 효과성 / 확장성 | 20 |
| 발표 / 전달력 | 10 |

최대 배점이 "멋있는가"가 아니라 **"실제로 동작하며 믿을 수 있는가"** 입니다.
그래서 연출 중심 화면(산점도·터미널·수사판 같은 시안)은 오히려 "목업 아닌가"라는
의심을 부릅니다. 대신 **신뢰성 자산을 화면 앞으로 끌어올립니다.**

| 화면에 반드시 남는 것 | 어디에 |
| --- | --- |
| 탈락한 주장과 사유 (`LedgerClaim.verdict === "rejected"`) | 검증 기록 |
| 검증 통과 비율 · 근거 커버리지 (`TraceScore`) | 검증 기록 스코어카드 |
| 주장 → Fact → Source → Evidence 계보 | 검증 기록 |
| 마스킹된 원본 근거 한 건 | 근거 드로어 |
| `dataset_version`, adapter 버전 | 검증 기록 재현 정보 |
| 계획 수정 횟수 (`planRevisions`) | 검증 기록 · 과정 보기 |
| **빗나간 예측** (`PredictionOutcome.verdict === "miss"`) | 액션 채점 리포트 |
| 근거 부족으로 값을 못 낸 지표 | 결과 화면에 "근거 부족"으로 |

> **전부 통과한 리포트는 검증하지 않은 리포트와 구분되지 않습니다.**
> 탈락·빗나감을 지우는 변경은 이 서비스의 주장을 스스로 무너뜨립니다.

---

## 5. 설계 원칙 여덟 개

화면을 고칠 때 이 목록과 충돌하면 화면이 아니라 이 문서를 먼저 고쳐야 합니다.

1. **숫자를 지어내지 않는다.** 근거가 없으면 값 대신 "근거 부족"을 표시합니다.
   (`Number.isNaN(metric.value)` → 점선 테두리)
2. **실패와 한계를 숨기지 않는다.** 탈락 주장, 빗나간 예측, 확인 못 한 소스,
   타임랩스가 데모 데이터라는 사실까지 화면에 적습니다.
3. **리포트는 스냅샷이지 대시보드가 아니다.** 액션을 적용해도 원본 리포트를 갱신하지
   않습니다. 갱신하면 "이 결론이 나온 과정"을 재현할 수 없습니다. 대신 기준 시점을
   명시하고(`periodLabel` · `analyzedAt`) 이후 변화는 맥락으로만 얹습니다.
4. **모든 주장은 원본 한 건까지 이어진다.** 깊이는 3단입니다 —
   Tier 1 근거 칩 → Tier 2 근거 드로어 → Tier 3 검증 기록.
5. **화면당 마젠타는 하나의 역할만.** 모두가 강조면 아무것도 강조가 아닙니다.
6. **카드는 면이 필요한 것에만.** 수치 비교는 표, 문단은 문단, 목록은 구분선.
7. **과정은 흘려보내되 되돌아올 자리를 남긴다.** 로딩은 지나가면 사라지므로
   결과 화면에 `ProcessTrace` 로 같은 기호·같은 문장을 다시 폅니다.
8. **한 페이지 안에서 해결한다.** 라우트를 쪼개면 전환 연출과 서사가 끊깁니다.
   phase 로 갈아끼우고 History API 로만 URL 을 맞춥니다.

## 6. 핵심 용어

| 용어 | 뜻 |
| --- | --- |
| **시그널(Signal)** | 여러 소스에 흩어진 행동을 하나로 묶은 고객 니즈의 신호 |
| **캐치(Catch)** | 시그널을 찾아내는 한 번의 분석 실행. 백엔드의 Run 하나에 대응 |
| **와쳐(Watcher)** | 알림 설정이 아니라 **"내 판단을 나중에 채점당하겠다"는 선언**. 조건을 매일 재실행하고, 지금 예측치를 박아 두고, 기간이 끝나면 실측과 대조해 적중/빗나감을 매긴다 |
| **실험(Experiment)** | 액션을 적용하고 관찰 중인 상태. `localStorage` 에 보관되며 Run 보다 오래 산다 |
| **브리핑(Briefing)** | 에이전트가 스스로 찾아 놓은 오늘의 시그널 묶음. 메인 화면 후보 |
| **Claim / Fact / Evidence** | 주장 / 검증된 사실 / 마스킹된 원본 근거. 백엔드 계약과 같은 뜻으로 씁니다 |

> 겹침 규칙은 코드의 `conflictOf` 하나입니다 — 같은 `segmentLabel` 을 이미 관찰
> 중이면 효과를 귀인할 수 없으므로 경고합니다. 세그먼트가 다르면 동시 진행을 막지
> 않습니다. ("슬롯 N칸 제한" 같은 게임 장치는 근거가 없어 폐기했습니다.)

## 7. 화면 서사

전체 흐름은 신청서의 `Detect → Understand → Recommend → Act` 가 한 바퀴 돌아 다시
Detect 로 이어지는 구조입니다.

```
 ┌── 브리핑 ──────────── 에이전트가 이미 잡아 둔 시그널 2건 (Detect)
 │      │
 │      ├── 이 시그널 확인하기 ──┐
 │      └── 비슷한 걸 더 찾기 ───┤
 │                              ▼
 └── 질문하기 ──────────────▶ 캐치하는 중 ──▶ 캐치 결과 (Understand)
                                             │      │
                                             │      ├─▶ 과정 보기 ─▶ 검증 기록
                                             │      │
                                             │      └─▶ 액션 (Recommend → Act)
                                             │             │
                                             │             ├ 미리보기: AS-IS ↔ TO-BE, 예측
                                             │             ├ 관찰: 타임랩스
                                             │             └ 채점: 적중/빗나감
                                             │                    │
                                             └────────────────────┘
                                        빗나간 예측이 다음 액션을 정당화 (다시 Detect)
```

### 단계별로 화면이 증명하려는 것

| 화면 | 증명 |
| --- | --- |
| 브리핑 | 묻지 않아도 먼저 찾아 놓는다 |
| 질문하기 | 자연어 한 줄이면 된다. 조건은 선택이지 필수가 아니다 |
| 캐치하는 중 | 지금 **실제로** 도구를 부르고 사실을 포착하고 있다 |
| 캐치 결과 | 결론이 있고, 근거가 있고, 못 한 것도 적혀 있다 |
| 검증 기록 | 12/14 통과. 탈락 2건의 사유까지 있다 |
| 액션 | 제안에서 끝나지 않는다. 예측을 박고 채점당한다 |

---

## 8. 메인 화면을 아직 확정하지 않았다

현재 기본 첫 화면은 **질문하기(`AskScreen`)** 이고, 브리핑은 `?main=briefing` 으로
켜 보는 상태입니다. (`use-catch-session.ts` 의 `DEFAULT_MAIN`)

| | 질문하기 | 브리핑 |
| --- | --- | --- |
| 첫인상 | 자유도 높음. 무엇이든 물어볼 수 있음 | 이미 일이 되어 있음 |
| 위험 | "또 하나의 검색창"으로 보임 | 시그널이 늘면 카드 목록이 무너짐 |
| 지금 상태 | 기본값 | 컴포넌트 완성, 데이터는 목업 2건 고정 |

**브리핑으로 전환할 때 바꿀 곳은 `DEFAULT_MAIN` 상수 하나뿐입니다.**
전환 판단 기준은 [03 §1](03-screen-specs.md) 에 있습니다.

폐기한 대안: 대시보드형 메인(옛날 빅데이터 UX로 읽힘), 시그널 카드 무한 목록
(개수가 늘면 전부 무너짐), 자유 질의를 별도 화면으로 분리(같은 화면 안에서 해결해야 함).
